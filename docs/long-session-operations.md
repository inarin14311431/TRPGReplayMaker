# 長時間TRPGセッションの録音・復旧運用

## 実装状態

- Discordの各発話ターンを個別PCM（audio/<meetingId>/<userId>_<startMs>.pcm）で保存。
- audio/<meetingId>/tracks.jsonl に開始・完了・中断のイベントを追記し、fsyncでディスクへ反映。
- 音声ファイルは書き込み完了後に確定。途中でBotプロセスが落ちた場合、残存するPCMを検証してリトライ可能。
- 文字起こし成功結果は音声ファイル単位でSQLiteに保存。再試行時、PCMのサイズと話者・時刻が一致する成功トラックは再利用。
- 未完了音声や一部失敗がある場合、会議ステータスを partial として扱い、完全成功を偽装しない。
- 終了済みセッションのPCMは既定30日間保持。AUDIO_RETENTION_DAYS=0 なら自動削除しない。失敗・partialは期間に関係なく保持。
- 保存期限は起動時と24時間ごとに判定。アプリ起動中の録音には触れない。

## 起動と運用

1. Windowsでは[Docker不要の利用マニュアル](user-manual.md)に沿って配布ZIPを展開、Bot接続と文字起こし方式（OpenAI APIまたは追加導入したローカルWhisper）を設定する。Docker Compose運用の場合は従来のコンテナー方式を利用する。
2. 既定の音声保持期間は30日（`AUDIO_RETENTION_DAYS=30`）。Windows配布版は `user-data/.env`、Docker版は環境設定で変更できる。長期保管時はディスク容量とアクセス権限を確認する。
3. 録音の前に参加者全員の同意を取得。公開リポジトリへ実音声、.env、保存DB、原文はコミットしない。
4. /join で録音開始、/leave で終了。トラックは発話ごとに記録される。
5. 予期しない終了後の会議はWeb UIで transcription_failed、一部が不確実なら partial と表示される。録音の再開ではなく、残存音声の文字起こしを再試行する。
6. 重要なリプレイは必ず音声と文字起こしを照合し、生成した原稿の誤認識を修正する。

## 検証可能な事柄／未検証の事柄

自動テストで、開始・終了ジャーナル、壊れた記録の無視、再起動後の録音断片検出、音声を残す保持期間、文字起こし済みトラックの再利用を確認する。

**実際のDiscordで12時間以上安定録音できるかは未検証**。本番運用前に長時間の通し試験が必要。推奨試験順: 30分→2時間→8時間→12時間。Botをプロセス強制終了して復旧する試験、同時発話、チャンネル離脱、ディスク容量不足も別途実機確認が必要。

注意: プロセスが停止した区間の音声は復元できない。既存コードによる録音中の発話を途中で細かく再分割する機能、OS障害時に必ず失われないことを保証する仕組み、外部バックアップへの自動アップロードは現段階では未実装。
